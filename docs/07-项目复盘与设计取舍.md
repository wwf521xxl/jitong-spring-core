# 07 · 项目复盘与设计取舍

## 1. 项目一句话

> 一套已经在 17 人左右小型工厂使用的计件生产系统：员工扫码报工，多人合报按人数平分，厂长看到真实生产进度，关键操作可追溯。

## 2. 背景与目标

工厂原来用纸单加 Excel 记录计件。人少时还能对，人一多就出现：

- 多人做同一道工序，产量算到谁头上容易有争议；
- 员工不知道自己今天做了多少；
- 订单走到哪一道，厂长只能靠问；
- 改单、补单、作废之后，历史记录对不上。

系统按“现场能用”设计，目标不是功能大而全，而是：

1. 报工路径短：扫码 → 选工序 → 报工成功；
2. 合报算得清：开组、加入、结束平分；
3. 进度实时：订单、工序、人员产量可查；
4. 数据可追溯：改单、作废、审批都有记录；
5. 部署简单：单厂、单实例、可备份、可恢复。

## 3. 关键取舍

### 3.1 为什么用 Spring Boot

- 工厂现场需要长期维护，Spring Boot 的生态、监控、部署和招聘都更成熟；
- Spring Security 能清楚表达“谁能做什么”；
- JPA + Flyway 让表结构和业务代码都有版本；
- 单 jar 部署，现场 Windows/Linux 都容易交付。

### 3.2 为什么权限必须在服务端

前端隐藏按钮只能改善体验，不能阻止直接调接口。所以：

- 管理员接口用 `@PreAuthorize("hasRole('ADMIN')")`；
- 建单人权限在 Service 层判断；
- 完成订单/结束合报要求“管理员或建单人”；
- 技能、数量、上游完成量都在服务端校验。

### 3.3 为什么合报要状态机

合报不是简单的“开/关”：

- 谁先开组；
- 谁加入了；
- 什么时候结束；
- 为什么结束；
- 有没有结算到一半。

把迁移集中到 `GroupStateMachine`，并写入 `job_step_group_events`，排障和审计都有据可查。非法迁移直接拒绝，不靠调用方自觉。

### 3.4 为什么结算放在事务里

单厂规模下，同步结算足够：

- 成员数量少；
- 一次结算只写几条记录；
- 失败必须整体回滚，不能出现半个人有记录。

规模上来后再考虑 Outbox + 异步重试，而不是现在引入 MQ 的复杂度。

### 3.5 为什么用 JWT + Cookie

- 浏览器端用 HttpOnly Cookie，避免把 token 暴露给 JS；
- 接口调用方可以用 `Authorization: Bearer`；
- Access Token 短、Refresh Token 长，前端无感续期；
- `token_version` 让退出、改密、停用能立即失效旧 token；
- 写请求做 Origin 校验，弥补没有 CSRF Token 的现状。

### 3.6 为什么用 JPA，不用 MyBatis-Plus

这个项目的复杂度在领域规则，不在 CRUD：

- 合报结算；
- 幂等与重复报工；
- 订单/工序/报工的状态校验；
- 乐观锁与事务边界。

JPA 的实体 + 仓储 + 事务更适合把规则收在 Service 层。如果团队已有 MyBatis 规范，替换持久层不影响 Controller 契约。

### 3.7 为什么不做微服务

单厂、17 人、单实例，拆微服务只会增加部署、网络和排障成本。先把模块边界和状态机做清楚，比拆服务更有价值。

## 4. 设计问答

### Q：管理员为什么不能建单？

前端文案、权限测试和现场流程都要求“排版人员建单，厂长只管理”。所以系统按产品规则实现：管理员不能建单；普通员工可以通过 `can_create_job` 获得建单权限；回收最后一名建单人会被拒绝。

### Q：合报并发结束怎么办？

组上有 `@Version` 乐观锁，两个 close 请求只有一个成功，失败方收到 `409 concurrent_update`；成员唯一约束防止重复加入；结算记录用 `GROUP-<groupId>-<employeeId>` 幂等键。

### Q：Cookie 认证没有 CSRF Token，怎么办？

- `SameSite=Lax`；
- 写请求 Origin 同源校验；
- JSON Content-Type；
- GET 不产生副作用。

这是当前前端形态下的折中。未来可以加 `/api/csrf` 并把 token 放进前端请求头。

### Q：JWT 怎么退出登录？

`token_version` 存在员工表，JWT 里带 `ver`；退出/改密/停用时递增，旧 token 全部失效。代价是全设备下线，单厂场景可接受；要做单设备下线再加 `jti` 黑名单。

### Q：旧 PIN 能直接升级吗？

能。PIN 哈希格式是 PBKDF2-SHA256：

```text
pbkdf2_sha256$160000$salt$digest
```

测试里有一组由历史实现生成的哈希做兼容校验。升级数据库后账号不需要重置密码；但早期浏览器会话不是 JWT，升级后需要重新登录一次。

### Q：为什么不用 Redis / MQ / 对象存储？

当前规模不需要：

- 登录限流在进程内，单实例够用；
- 合报同步结算，事务内完成；
- 照片存本地磁盘，数据量小。

这些都在“下一步”里，而不是为了技术栈完整而提前引入。

## 5. 复盘

### 做得好的

- 订单保存路线快照，改路线不影响历史订单；
- 合报从布尔开关变成可测试的状态机；
- 报工和结算都有幂等键，网络重试不会重复记账；
- 权限在服务端校验，并有测试覆盖；
- 文档记录了“为什么”，不是只列技术栈。

### 可以更好的

- 数据导入工具还停留在导出/对账设计，没有做完整的自动导入；
- Docker 镜像需要在目标环境实际构建验证；
- 并发 close 只做了乐观锁，没有压测；
- 真实 PostgreSQL 的集成测试还没接 Testcontainers；
- 前端截图和演示数据的订单号不完全一致。

## 6. 本地演示顺序

1. 用 `7 / 123456` 登录，新建 `m²` 订单；
2. 自动报工第 1、2 道；
3. 第 3 道「写真过板」开合报组；
4. 用 `9 / 123456` 登录，加入合报；
5. 用 `admin / Admin@123456` 结束合报，两人各一半；
6. 打开 `/api/docs` 或审计接口，看状态迁移与操作记录；
7. 用 `4 / 123456` 登录，验证普通员工不能建单、不能调管理接口。
